# المعمارية التقنية
## النظام الوطني لإدارة مؤشرات الأداء الصحي والجودة وسلامة المرضى في اليمن

**الإصدار:** 1.0 — المرحلة الأولى · **الحالة:** مسودة بانتظار الموافقة

---

## الشرح بلغة بسيطة
المعمارية هي **المخطط الهندسي** للنظام: ما الأجزاء؟ كيف تتحدث مع بعضها؟ وأين تُخزَّن البيانات؟
نظامنا له **ثلاثة أجزاء**: (1) برنامج على جهاز كل مستشفى، (2) خادم مركزي، (3) قاعدة بيانات مركزية.
البرنامج المحلي يعمل **مستقلاً تماماً** دون إنترنت، وعند توفر الاتصال يرسل **تغييراته فقط** للخادم.

## 2. المكوّن 1: تطبيق سطح المكتب (Tauri)

### 2.1 لماذا Tauri؟
- **حجم صغير** (ميغابايتات قليلة) — مهم للأجهزة الضعيفة والتنزيل عبر إنترنت بطيء.
- **يعمل دون إنترنت** بالكامل (لا يحتاج خدمات سحابية).
- **Rust في النواة** يمنح أماناً وأداءً للمنطق الحسّاس (المزامنة، التشفير).
- **WebView النظام** يوفّر واجهة React غنية دون حزم ثقيلة.
- دعم جيد لتطبيقات Windows والتوقيع والتحديث.

### 2.2 توزيع المسؤوليات داخل التطبيق
| الطبقة | التقنية | المسؤولية |
|-------|--------|-----------|
| الواجهة | React + TypeScript | العرض، الإدخال، RTL، الرسوم (ECharts) |
| الجسر | Tauri IPC (أوامر) | استدعاء آمن للوظائف من الواجهة |
| النواة | Rust | المنطق، التحقق، الوصول لقاعدة البيانات، المزامنة، التشفير |
| التخزين | SQLite + ملفات | البيانات محلياً |

**قاعدة:** الواجهة **لا تلمس قاعدة البيانات مباشرة**؛ تمرّ دائماً عبر النواة (Rust) — هذا يحمي المنطق ويمنع ثغرات.

### 2.3 وحدات النواة المحلية (Rust)
- `db` — الوصول لـ SQLite، المخططات، الترحيلات، المعاملات.
- `auth` — الدخول المحلي، الجلسات، تجزئة كلمات المرور.
- `indicators` — تعريف المؤشرات وحساب القيم.
- `periods` — الفترات وسير العمل (مسودة/مراجعة/اعتماد).
- `quality` — الحوادث، RCA، CAPA، المخاطر، التدقيق، الوثائق، الاجتماعات.
- `reports` — توليد PDF/Excel محلياً.
- `sync` — طابور التغييرات، دفع/سحب، معالجة التعارض.
- `backup` — النسخ الاحتياطي والاستعادة.
- `ai` — واجهة المساعد (تجميع البيانات + إرسال/عرض النتائج).

## 3. المكوّن 2: الخادم المركزي (FastAPI — Modular Monolith)

### 3.1 لماذا Modular Monolith؟
- **أبسط في البداية:** نشر واحد، قاعدة بيانات واحدة، تتبّع أخطاء أسهل.
- **قابل للتوسع لاحقاً:** كل وحدة معزولة بحدود واضحة، فيمكن فصلها لخدمة مستقلة لاحقاً **دون إعادة بناء**.

### 3.2 الوحدات (Modules)
| الوحدة | المسؤولية |
|-------|-----------|
| `identity` | المستخدمون، الأدوار، الصلاحيات، الدخول |
| `organization` | المستويات الإدارية، المستشفيات، الأقسام |
| `indicators` | مكتبة المؤشرات، الإصدارات، الأنواع |
| `submissions` | إدخالات الفترات، سير العمل، الاعتماد |
| `quality` | الحوادث، RCA، CAPA، المخاطر، التدقيق، الوثائق، الاجتماعات |
| `sync` | نقاط الدفع/السحب، حل التعارض، الفوترة المنطقية |
| `reporting` | التجميع، المقارنات، التصدير |
| `notifications` | التنبيهات والإشعارات |
| `ai` | التجميع التحليلي وواجهة المساعد |
| `audit` | سجل التدقيق |
| `admin` | إدارة النظام والنسخ الاحتياطي |

**قاعدة الحدود:** كل وحدة تتعامل مع جداولها فقط، وتتواصل مع غيرها عبر واجهات داخلية واضحة (Application Services)، لا عبر جداول بعضها.

### 3.3 مبادئ التصميم
- **Data over code:** المكتبات (المؤشرات، أنواعها، الحدود) جداول بيانات لا شروط مكتوبة في الكود.
- **Extend through seams:** إضافة نوع مؤشر/وحدة/مصدر بيانات جديدة عبر واجهة (Interface) مسجّلة في مكان واحد.
- **Structured results:** القرارات على حقول مُصنَّفة لا على نص إنجليزي.
- **Versioned files:** كل ملف مُصدَّر فيه إصدار ومخطط ومسار ترقية.

## 4. المكوّن 3: المنصة المركزية (Web Portal)

- **React + TypeScript** + **ECharts** للرسوم.
- تتحدث مع FastAPI عبر REST.
- واجهاتها: لوحة قيادة وطنية، مقارنات، إدارة مستشفيات/أقسام/مستخدمين، مكتبة المؤشرات، تقارير، متابعة المتأخرين.
- **كل عرض مُقيَّد بالصلاحية** على الخادم (لا الاعتماد على الواجهة فقط).

## 5. نموذج البيانات المُشترك (مفهومي)

الكيانات الأساسية في الطرفين (تفصيلها في الوثيقة 05):

```
Organization (مستوى إداري) ──< Hospital ──< Department ──< UserAssignment

Meeting ──< MeetingDecision ──< FollowUp

SyncQueue / SyncCursor / ChangeLog (المزامنة)
```

## 6. تدفق العمل الرئيسي (End-to-End)

```
1) مسؤول القسم يدخل قيمة مؤشر لفترة  →  تُحسب النتيجة فوراً  →  تُحفظ محلياً (SQLite)
2) يرسل للمراجعة  →  إشعار لمدير الجودة  →  يراجع/يعتمد أو يعيد
3) تُسجَّل كل خطوة في سجل التدقيق المحلي
4) عند توفر الإنترنت: خدمة المزامنة ترسل التغييرات (فقط) للخادم
5) الخادم يتحقق، يمنع التكرار، يحل التعارض، ويحدّث PostgreSQL
6) المنصة المركزية تُحدّث اللوحات والتقارير
7) المساعد يحلّل الأرقام ويعرض اتجاهات/شذوذ/ملخصات (مسندة للبيانات)
```

## 7. النشر (Deployment)

### 7.1 الخادم (Docker Compose)
```
services:
  api        (FastAPI + Uvicorn/Gunicorn)
  db         (PostgreSQL)
  storage    (MinIO أو مجلد مُدار للمرفقات)
  proxy      (Nginx/Reverse Proxy + TLS)
  backup     (مهمة نسخ احتياطي مجدولة)
```
- **TLS إلزامي** لكل الاتصالات.
- **أسرار** في متغيّرات بيئة/مدير أسرار، لا في الكود.
- **نسخ احتياطي** مجدول لقاعدة البيانات والتخزين، مع نسخة بعيدة.

### 7.2 تطبيق المستشفى
- حزمة تثبيت Windows (MSI/EXE) موقّعة إن أمكن.
- تحديثات آلية عبر قناة موثوقة (تُنزَّل عند توفر الإنترنت).
- قاعدة البيانات المحلية في مجلد بيانات المستخدم، مع نسخ احتياطي محلي.

---

## 8. اعتبارات الأداء والتوسع
- **محلياً:** SQLite يكفي لمستشفى واحد (ملايين السجلات بأداء جيد).
- **مركزياً:** PostgreSQL + فهارس مناسبة + ترقيم صفحات + تجميع مسبق للتقارير الثقيلة.
- **التوسع الأفقي لاحقاً:** يمكن فصل `reporting` و `ai` و `sync` إلى خدمات مستقلة عند الحاجة.
- **التخزين المؤقت:** طبقة كاش للوحات الثقيلة (Redis اختياري لاحقاً).

## 9. قرارات معمارية مسجّلة (ADR مختصر)

| # | القرار | السبب |
|---|-------|-------|
| ADR-1 | Tauri بدل Electron | حجم أصغر وأداء أفضل على أجهزة ضعيفة |
| ADR-2 | SQLite محلياً | عمل دون إنترنت + معاملات آمنة |
| ADR-3 | Modular Monolith أولاً | بساطة البداية مع قابلية الفصل لاحقاً |
| ADR-4 | UUIDv7 للمعرّفات | فريد عالمياً + مرتب زمنياً (أفضل للفهارس والمزامنة) |
| ADR-5 | مزامنة تزايدية بطابور تغييرات | تقليل البيانات + استئناف بعد الانقطاع |
| ADR-6 | RLS في PostgreSQL | عزل صارم لبيانات المستشفيات |
| ADR-7 | تحليل الشذوذ حسابياً + الذكاء للصياغة | منع الاختلاق وأمانة النتائج |
| ADR-8 | لا بيانات شخصية للمرضى | خصوصية + تقليل المخاطر القانونية |
| ADR-9 | REST + نقاط مزامنة مخصّصة | بساطة وتوافق + كفاءة المزامنة |

## 10. حدود واضحة مع الأنظمة القائمة
- **لا نستبدل DHIS2**؛ يمكن لاحقاً بناء مُصدِّر متوافق معه (تسليم خلاصة المؤشرات).
- **لا نخزّن بيانات مرضى فردية**؛ القياس مُجمّع.
- **لا نلمس** أنظمة التراخيص/الاعتماد الرسمية.

---

## 11. ما لن نلتزم به في المرحلة الأولى (بوضوح)
- خدمات مصغّرة (Microservices) منفصلة.
- تكامل حي مع أجهزة طبية.
- تطبيق موبايل.
- تعلم آلي مدرّب على بيانات حقيقية.
