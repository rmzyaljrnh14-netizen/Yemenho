# مواصفات بروتوكول المزامنة (تفصيلي)
## النظام الوطني لإدارة مؤشرات الأداء الصحي والجودة وسلامة المرضى — وزارة الصحة العامة والسكان

**الإصدار:** 1.1 · **الحالة:** مسودة بانتظار الموافقة

> هذه الوثيقة هي **المواصفة التقنية الكاملة** للمزامنة. الوثيقة 07 تشرح الفكرة؛ وهذه تحدّد التفاصيل الدقيقة للتنفيذ.

---

## 1. نموذج البيانات والمصطلحات
| المصطلح | المعنى |
|--------|--------|
| `node` | جهاز/تطبيق مستشفى له معرّف فريد |
| `rev` | رقم مراجعة السجل (يزيد محلياً مع كل تعديل) |
| `outbox` | طابور العمليات المحلية غير المُرسَلة |
| `change_log` | سجل تغييرات الخادم المتسلسل (`server_seq`) |
| `cursor` | مؤشّر آخر `server_seq` سحبه الجهاز |
| `op` | العملية: `upsert` أو `delete` |
| `idem_key` | مفتاح منع التكرار |

## 2. دورة حياة العملية (State Machine)
```
local ──(تعديل)──▶ pending ──(إرسال)──▶ sending ──(تأكيد)──▶ synced
                      ▲                     │
                      │                     ├─(رفض)──▶ rejected  (يُعرض للمستخدم)
                      └──(إعادة محاولة)─────┤
                                            └─(تعارض)─▶ conflict ──(حل)──▶ synced
```

## 3. هيكل الطابور المحلي (outbox)
```json
{
  "id": "0190op...",
  "entity_type": "period_value",
  "entity_id": "0190pv...",
  "op": "upsert",
  "base_rev": 1,
  "payload": { "...الحالة الكاملة للسجل..." },
  "created_at": "2026-11-07T20:00:00Z",
  "attempts": 0,
  "state": "pending",
  "last_error": null
}
```
**قواعد:**
- كل تعديل يضيف عملية **جديدة** (لا نعدّل عملية قديمة) لضمان الترتيب.
- تُدمج العمليات المتتالية على نفس السجل عند الإرسال (نرسل الأحدث فقط) **إن** كان ذلك آمناً (نفس `entity_id` ولم يُرسَل بعد).
- `delete` لا يحمل حذفاً فعلياً؛ يحمل `deleted_at`.

```json
{

  "sent_at": "2026-11-07T20:05:00Z",
  "operations": [
    {
      "op_id": "0190op-1",
      "entity_type": "period_value",
      "entity_id": "0190pv-1",
      "op": "upsert",
      "base_rev": 1,
      "payload": { "...": "..." }

    { "op_id": "0190op-2", "entity_type": "incident", "entity_id": "0190inc-1", "op": "upsert", "base_rev": 0, "payload": { "...": "..." } },
    { "op_id": "0190op-3", "entity_type": "capa_action", "entity_id": "0190cap-1", "op": "upsert", "base_rev": 0, "payload": { "...": "..." } },
    { "op_id": "0190op-4", "entity_type": "risk", "entity_id": "0190rsk-1", "op": "upsert", "base_rev": 1, "payload": { "...": "..." } },
    { "op_id": "0190op-5", "entity_type": "audit", "entity_id": "0190aud-1", "op": "upsert", "base_rev": 0, "payload": { "...": "..." } },
    { "op_id": "0190op-6", "entity_type": "improvement_plan", "entity_id": "0190imp-1", "op": "upsert", "base_rev": 0, "payload": { "...": "..." } },
    { "op_id": "0190op-7", "entity_type": "improvement_action", "entity_id": "0190ima-1", "op": "upsert", "base_rev": 0, "payload": { "...": "..." } }
  ]
}
```
> الكيانات القابلة للدفع من الجهاز: `period_value` و`reporting_period` و`incident`
> و`capa_action` و`risk` (v0.14) و`audit` و`improvement_plan` و`improvement_action` (v0.15).
> أي نوع آخر يُرفَض بـ`rejected: unsupported_entity`.
### 4.2 الرد
```json
→ 200
{
  "batch_id": "0190batch-...",
  "server_seq": 58213,
  "results": [
    { "op_id": "0190op-1", "status": "applied",  "new_rev": 2 },
    { "op_id": "0190op-2", "status": "conflict", "current_rev": 3,
      "server_payload": { "...الحالة على الخادم..." },
      "reason": "rev_stale" },
    { "op_id": "0190op-3", "status": "rejected", "reason": "forbidden" }
  ]
}
```
### 4.3 قواعد الخادم عند الدفع
1. **تحقق المصادقة والتخويل** (هل الجهاز/المستخدم مسموح بهذا النوع؟).
2. **تحقق من Idempotency:** إن سبق تطبيق `op_id` → `applied` بلا أثر مزدوج.
3. **تحقق من `base_rev` مقابل `rev` الحالي:** إن أحدث → `conflict`.
4. **تحقق من قواعد العمل:** (فترة معتمدة؟ صلاحية؟ مقام صفر؟) → `rejected`.
5. **التطبيق داخل معاملة (transaction) ذرّية** لكل عملية.
6. **كتابة `change_log`** برقم `server_seq` متسلسل.
7. **إرجاع النتائج** لكل عملية.

> **ذرّية الدفعة:** كل عملية تُطبَّق مستقلة؛ فشل عملية لا يُسقط البقية، لكن كل عملية إما تنجح كاملة أو لا.

## 5. نقطة السحب: `GET /sync/pull`
### 5.1 الطلب
```
GET /api/v1/sync/pull?since=58100&limit=500&hospital_id=0190h...
```
### 5.2 الرد
```json
→ 200
{
  "from_seq": 58101,
  "to_seq": 58213,
  "has_more": false,
  "changes": [
    { "server_seq": 58101, "entity_type": "indicator", "entity_id": "0190i-5", "op": "upsert", "rev": 3, "payload": { "...": "..." } },
    { "server_seq": 58102, "entity_type": "indicator_version", "entity_id": "0190iv-9", "op": "upsert", "rev": 1, "payload": { "...": "..." } }
  ]
}
```
### 5.3 ماذا يُسحب؟
- تحديثات **المكتبة الوطنية** للمؤشرات والأهداف.
- تغييرات إدارية تخصّ المستشفى (أقسام/مستخدمون).
- تنبيهات موجّهة.
- **لا** يُسحب ما يملكه المستشفى أصلاً (لتقليل الحمل) — إلا عند طلب مزامنة كاملة.

## 6. اكتشاف التعارض
### 6.1 الشروط
يُعتبر تعارضاً إذا:
- `base_rev` المُرسَل **أقدم** من `rev` الحالي على الخادم، **و**
- السجل من نوع **قابل للتعارض** (بيانات إدخال/جودة).

### 6.2 قواعد الحل (تفصيلية)
| النوع | الحقل | القاعدة | النتيجة |
|------|------|--------|--------|
| period_value (غير معتمد) | القيمة/البسط/المقام | آخر تعديل يفوز | يُطبَّق الأحدث، والقديم يُحفظ في `conflict_log` |
| period_value (معتمد) | أي تعديل | يُرفض محلياً | `rejected: already_approved` |
| incident / capa / risk / audit / plan | حقول نصية | دمج حقل-بحقل | حقول مُختلفة تُدمج؛ نفس الحقل → يفوز الأحدث + يُسجَّل |
| indicator (وطني) | أي تعديل | الخادم هو المرجع | `rejected: server_authoritative` |
| departments/users | أي تعديل | الخادم هو المرجع | `rejected` أو تطبيق نسخة الخادم |
| documents | الملف/الإصدار | إصدار جديد | يُنشأ إصدار منفصل بدل الاستبدال |

### 6.3 جدول سجل التعارض
```sql
CREATE TABLE conflict_log (
  id            TEXT PRIMARY KEY,
  entity_type   TEXT, entity_id TEXT,
  node_id       TEXT,
  local_payload TEXT,      -- نسخة المستشفى
  server_payload TEXT,     -- نسخة الخادم
  resolution    TEXT,      -- 'auto_local','auto_server','field_merge','manual'
  resolved_by   TEXT,      -- المستخدم إن كان يدوياً
  resolved_at   TIMESTAMP,
  created_at    TIMESTAMP
);
```

### 6.4 التعارض اليدوي
- إن لم تنطبق قاعدة تلقائية → يُعرض السجل في **سجل التعارضات** بالنسختين.
- المسؤول يختار: (استخدام المحلي / استخدام المركزي / دمج يدوي).
- يُسجَّل القرار والمُنفّذ.
- **لا يُحذف أي شيء صامتاً أبداً.**

## 7. منع التكرار (Idempotency) — التفصيل
- **مفتاح العملية:** `op_id` فريد لكل عملية (UUIDv7).
- **الخادم يحفظ** كل `op_id` مُطبَّق في جدول `sync_idempotency` مع النتيجة.
- **إعادة الإرسال:** إن وُجد `op_id` → يعيد **نفس النتيجة المحفوظة** بلا تطبيق مزدوج.
- **حد الاحتفاظ:** يُحفظ المفتاح لمدة كافية (مثلاً 90 يوماً) ثم يُنظَّف بأمان.

## 8. الدفعات والأداء
| المعامل | القيمة الافتراضية | قابل للضبط |
|--------|------------------|-----------|
| حجم الدفعة (عمليات) | 50 | نعم |
| حجم الدفعة (بايت) | 1 ميغابايت | نعم |
| حجم السحب | 500 تغيير | نعم |
| مهلة الطلب | 30 ثانية | نعم |
| إعادة المحاولة | تصاعدية (1s, 2s, 4s, …, بحد 5 دقائق) | نعم |
| حد المحاولات | 8 ثم يُعلَّم فاشلاً ويُعرض | نعم |

**الضغط:** يُضغط جسم الطلب (gzip) لتفادي إثقال الشبكة الضعيفة.

## 9. التعامل مع الانقطاع (Resilience)
1. **انقطاع قبل الإرسال:** العمليات تبقى `pending`؛ لا شيء يُفقد.
2. **انقطاع أثناء الإرسال:** لا تأكيد → تُعاد المحاولة بنفس `op_id` (آمن).
3. **انقطاع أثناء الرد:** الخادم قد يكون طبّق فعلاً → إعادة الإرسال تُكتشف بـ Idempotency.
4. **تعطّل الخادم:** المحلي سليم؛ يُعاد المحاولة عند عودة الخادم.
5. **إعادة تشغيل الجهاز:** الطابور محفوظ على القرص؛ يُستأنف.

## 10. المزامنة الكاملة (Full Sync)
- عند جهاز جديد أو استعادة نسخة: مزامنة كاملة أولية.
- `POST /sync/bootstrap` → يعيد بيانات المكتبة الوطنية والإدارية اللازمة للبدء.
- بيانات المستشفى تُرفع من الطابور المحلي.
- **الحجم الكبير:** على دفعات مع تقدّم مرئي.

## 11. النقل الفيزيائي (T4) — الحزمة
للمستشفيات بلا إنترنت:
1. التطبيق يُصدّر **حزمة مشفّرة** (`bundle`) تحتوي عمليات الطابور + توقيع.
2. تُنقل على وحدة تخزين (USB) إلى مركز اتصال (محافظة/الوزارة).
3. يُستورد عبر `POST /sync/import-bundle`.
4. **نفس منطق Idempotency** يمنع التكرار.
5. تُعاد حزمة "سحب" لترقية بيانات المكتبة الوطنية على جهاز المستشفى.

**أمان الحزمة:** تشفير بمفتاح، توقيع للتأكد من المصدر، ورفض أي حزمة غير موقّعة أو معدّلة.

## 12. المراقبة والشفافية
- `GET /sync/status` يعيد: آخر مزامنة، عدد pending، آخر خطأ، آخر `server_seq`.
- **تطبيق المستشفى يعرض** شريط حالة دائم (متصل/غير متصل، آخر مزامنة، المتبقّي، الأخطاء).
- **الوزارة ترى:** المستشفيات المتأخرة، حجم المزامنة، الأخطاء المتكررة.

## 13. أمن المزامنة
- TLS إلزامي، ورفض الاتصال غير المشفّر.
- مصادقة الجهاز (مفتاح جهاز) + المستخدم.
- الحزم الفيزيائية: تشفير + توقيع + رفض المعدّل.
- تسجيل كل عملية مزامنة في سجل التدقيق.
- صلاحيات: الجهاز لا يرسل إلا أنواعاً مسموحاً بها، ولا لمستشفى غير مستشفاه.

## 14. اختبارات المزامنة المطلوبة (تفصيل)
| # | السيناريو | النتيجة المطلوبة |
|---|----------|------------------|
| S1 | كتابة ثم قطع كهرباء فوري | لا فقدان |
| S2 | أسبوع بلا إنترنت | كل شيء pending ثم يُرسَل |
| S3 | إرسال دفعة ثم نجاح | synced بلا تكرار |
| S4 | قطع وسط الإرسال | استئناف بلا تكرار/فقدان |
| S5 | إرسال نفس الدفعة مرتين | لا تكرار (idempotent) |
| S6 | تعديل متزامن محلي/مركزي | تعارض محلول بقاعدة |
| S7 | تعديل فترة معتمدة | مرفوض، المعتمد ثابت |
| S8 | جهازان نفس المستشفى | لا فقدان، دمج/تعارض |
| S9 | استعادة من نسخة | مزامنة تُكمل بسلام |
| S10 | تعطّل الخادم | المحلي سليم، إعادة لاحقاً |
| S11 | حزمة USB معدّلة | مرفوضة (توقيع) |
| S12 | حزمة USB مكرّرة | لا تكرار |
| S13 | دفعة 10 آلاف عملية | تعالج على دفعات بلا تعطّل |
| S14 | مقام = صفر | مرفوض برسالة واضحة |
| S15 | تعارض حقول متعددة في حادث | دمج حقل-بحقل بلا فقدان |

## 15. قواعد ذهبية (للمطوّر)
- **اكتب محلياً أولاً، دائماً.**
- **كل عملية قابلة للتكرار بأمان (idempotent).**
- **لا حذف فعلي؛ حذف منطقي.**
- **الخادم مرجع الوطني؛ المستشفى مرجع بياناته.**
- **لا قرار صامت في التعارض؛ إما قاعدة معلنة أو حسم بشري مسجّل.**
- **المستخدم يرى الحقيقة كاملة.**

## 16. حالة التنفيذ (v0.6 — مُنفَّذ ومُختبر)

هذا القسم يوثّق ما بُني فعلاً وما اختُبر، وليس خططاً.

### الخادم (Backend)
- **جداول جديدة** (`backend/migrations/007_sync.sql`): `change_log` (ترتيب عالمي `server_seq`)، `sync_idempotency` (منع التكرار)، `conflict_log` (سجل التعارضات)، `sync_nodes` (أجهزة المستشفيات) — مع سياسات RLS.
- **واجهات** (`app/api/sync.py`): `POST /sync/push`، `GET /sync/pull`، `POST /sync/bootstrap`، `GET /sync/status`.
- **المنطق** (`app/services/sync.py`): تطبيق العمليات، منع التكرار بـ `op_id`، كشف التعارض بـ `base_rev` مقابل `rev`، حماية الفترات المُرسلة/المعتمدة، وإعادة تطبيق سياق RLS بعد كل `commit` (إعدادات المعاملة المحلية تُصفَّر بعد الإيداع).
- **ربط الكتابة المباشرة:** كتابات الواجهة العادية (إنشاء فترة، حفظ/حذف قيمة، انتقالات دورة العمل) تُسجَّل في `change_log` أيضاً، فتنتشر التعديلات المباشرة والمحلية على السواء.
- **الاختبارات:** 12 اختبار مزامنة أساسية (منها: `base_rev` قديم ⇒ تعارض لا استبدال؛ فترة معتمدة ترفض تعديلاً محلياً؛ مقام صفر يُخزَّن فارغاً؛ السحب بعد مؤشّر؛ إعادة إرسال الدفعة لا تُكرّر)، إضافةً إلى اختبارات الحوادث (`test_sync.py`) واختبارات CAPA والمخاطر (`test_sync_quality.py`، v0.14) واختبارات التدقيق وخطط التحسين (`test_sync_audit_plan.py`، v0.15).
- **الكيانات القابلة للدفع حالياً:** `reporting_period` و`indicator_value` و`incident` و`capa_action` و`risk` و`audit` و`improvement_plan` و`improvement_action`. المكتبة الوطنية والإسنادات تُسحَب للقراءة فقط في هذه المرحلة.

### تطبيق سطح المكتب (Desktop)
- **المخزن المحلي** (`desktop/src-tauri/src/store.rs`): SQLite عبر `rusqlite` (bundled)، جداول: `local_period`، `local_value`، `local_incident`، `local_capa`، `local_risk`، `local_audit`، `local_plan`، `local_plan_action`، `library` (مؤشرات/أقسام/مستشفيات/إسنادات)، `outbox`، `meta`، `conflict`.
- **الحساب المحلي:** يطبّق نفس قواعد الخادم (النسبة/المعدل/العدد/المتوسط/المجموع/المدخل، والاتجاه: ارتفاعه أفضل/انخفاضه أفضل/نطاق) فيعمل التقييم دون إنترنت.
- **الصندوق الصادر:** كل حفظ يُسجَّل عمليةً بمعرّف فريد وحالة (`pending`/`failed`/`synced`)، ويُبقي `base_rev` لأحدث قيمة ليعمل كشف التعارض.
- **المحرّك** (`desktop/src/sync.ts`): دفع العمليات المعلّقة، ثم سحب تغييرات الخادم بعد مؤشّر محفوظ مع التعامل مع التعارض والمرفوض، والتهيئة الأولى عند المؤشّر صفر.
- **الربط بالواجهة** (`desktop/src/useSync.ts` + `pages/SyncSettings.tsx`): تشغيل تلقائي عند الإقلاع وكل دقيقة وعند حدث `online`، ومؤشّر حالة في الشريط العلوي، وصفحة تفصيلية مع «مزامنة الآن» ونسخة احتياطية محلية.
- **الاختبارات:** 24 اختبار Rust (الحساب، التقييم، الصندوق الصادر، إعادة الحفظ تُحدّث `base_rev`، التعارض يُسجَّل ولا يُفقَد، حفظ/سحب الحوادث وإجراءات CAPA والمخاطر والتدقيق وخطط التحسين وخطواتها، البقاء بعد إعادة فتح القاعدة).

### ما لم يُنفَّذ بعد في المزامنة (بصراحة)
- دفع المؤشرات/الإسنادات/المستخدمين من الجهاز إلى الخادم (حالياً سحب فقط لهذه الكيانات).
- دمج الحقول حقل-بحقل (field-level merge) في التعارضات؛ الحالي: نسخة الخادم تفوز وتُسجَّل.
- المزامنة عبر حزمة USB للأماكن بلا شبكة إطلاقاً.
- تشفير البيانات في السكون (at rest) على جهاز المستشفى.

> **v0.12:** صار سجل التعارضات **مرئياً وقابلاً للمعالجة** عبر «مركز المزامنة الوطني»
> (`docs/26-sync-monitor.md`): حالة الأجهزة (منتظم/متأخر) والتعارضات المفتوحة، مع تسجيل
> المراجعة في سجل التدقيق دون تغيير أي بيانات. يبقى الدمج حقل-بحقل غير منفَّذ.

> **v0.13:** صار محرّك التنبيه **ينبّه من تلقاء نفسه** عند تعطّل المزامنة: جهاز لم
> يُزامن منذ العتبة (`stale_device`) أو تعارضات لم يراجعها مسؤول (`open_conflict`)،
> محسوبةً من نفس الجدولين وبعتبات قابلة للتهيئة (`docs/27-sync-alerts.md`).

> **v0.14:** امتدّت المزامنة دون إنترنت إلى **إجراءات CAPA والمخاطر**: صار بإمكان
> موظف الجودة إدخالهما دون اتصال (يُكتبان في `local_capa`/`local_risk` ويُدرَجان في
> الصندوق الصادر)، ويُدفعان عند عودة الشبكة، وتُطبَّق نسخ الخادم عند السحب — بنفس
> منطق الحوادث (`rev`، كشف التعارض، فرض نطاق المستشفى). الترحيل `016_quality_sync.sql`
> يضيف عمود `rev` إلى `capa_actions` و`risks`.

> **v0.15:** امتدّت المزامنة دون إنترنت إلى **التدقيق الداخلي وخطط التحسين وخطواتها**:
> يكتب موظف الجودة التدقيق وخطة التحسين وخطواتها محلياً (`local_audit`/`local_plan`/
> `local_plan_action`) وتُدرَج في الصندوق الصادر، وتُدفع عند عودة الشبكة وتُطبَّق نسخ
> الخادم عند السحب — بنفس منطق الحوادث. الخطوة مرتبطة بخطتها (`plan_id`) ولا تُنقل
> بين الخطط؛ الرمز والدرجة وحالة الاعتماد مملوكة للخادم. الترحيل
> `017_audit_plan_sync.sql` يضيف عمود `rev` إلى `quality_audits` و`improvement_plans`.

> تُحدَّث هذه القائمة مع كل مرحلة، ولا ندّعي عمل ما لم يُنفَّذ ويُختبَر.
