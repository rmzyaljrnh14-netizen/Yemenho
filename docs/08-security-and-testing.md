# الأمان والصلاحيات وخطة الاختبار
## النظام الوطني لإدارة مؤشرات الأداء الصحي والجودة وسلامة المرضى في اليمن

**الإصدار:** 1.0 — المرحلة الأولى · **الحالة:** مسودة بانتظار الموافقة

---

## الشرح بلغة بسيطة
الأمان يعني **ألا يرى أحد ما لا يحق له، وألا يغيّر أحد ما لا يحق له، وأن نعرف من فعل ماذا**.
والاختبار يعني **أن نتأكد فعلياً** أن كل شيء يعمل قبل أن نقول إنه يعمل.

# الجزء الأول: الأمان

## 1. مبادئ الأمان
1. **الحد الأدنى من الصلاحية:** كل مستخدم يحصل على أقل صلاحية تكفيه.
2. **الدفاع بطبقات:** الحماية في الواجهة **و** في الخادم **و** في قاعدة البيانات.
3. **لا ثقة بالعميل:** الواجهة تُخفي فقط؛ القرار النهائي دائماً على الخادم.
4. **الأمانة والتتبّع:** كل عملية حساسة مسجّلة.
5. **الخصوصية أولاً:** لا بيانات شخصية للمرضى.

## 2. المصادقة (Authentication)
- كلمة مرور مُجزّأة بـ **Argon2id** (أو bcrypt كبديل) — لا تُخزَّن كنص أبداً.
- سياسة قوة كلمة المرور (طول + تعقيد معقول).
- قفل الحساب مؤقتاً بعد عدد محاولات فاشلة.
- جلسات قصيرة العمر + تجديد آمن + إنهاء عند الخمول.
- عند العمل دون إنترنت: **جلسة محلية موثوقة مسبقاً** محدودة الصلاحيات ومحدودة المدة.
- (اختياري مستقبلاً) مصادقة ثنائية للمديرين المركزيين.

## 3. التخويل (Authorization)
- **أدوار** جاهزة (انظر القسم 5) + **صلاحيات دقيقة** على مستوى العملية.
- التخويل يُطبَّق على الخادم لكل نقطة API.
- **عزل المستشفيات:** لا يمكن لمستخدم مستشفى الوصول لبيانات غيره.
- الإدارة المركزية ترى المُجمَّع/المسموح فقط وفق دورها.

## 4. عزل البيانات (Data Isolation)
- في PostgreSQL: **أمان مستوى الصف (RLS)** يقيّد كل استعلام بنطاق المستخدم (مستشفى/محافظة).
- سياق المستخدم (`hospital_id`, `role`) يُضبط لكل اتصال/طلب.
- استعلام بلا سياق صحيح → يعيد **صفر صفوف** (لا يعيد الكل) — قاعدة أمان.
- **اختبارات عزل إلزامية:** كل دور يُختبر أنه لا يرى ما لا يحق له.

## 6. حماية واجهات API
- **مصادقة:** رمز وصول قصير العمر + رمز تحديث.
- **تحديد المعدّل (Rate limiting):** لمنع الإساءة والهجوم.
- **التحقق من المدخلات:** كل مدخل يُتحقق منه (نوع/طول/نطاق) على الخادم.
- **منع الوصول غير المصرّح:** رفض + تسجيل.
- **CORS مُقيَّد** بالنطاقات المسموحة.
- **رؤوس أمان:** HSTS، CSP، X-Content-Type-Options…

## 7. تشفير البيانات
| الحالة | الإجراء |
|-------|--------|
| أثناء النقل | TLS 1.2+ إلزامي |
| محلياً (سطح المكتب) | SQLCipher/تشفير حقول حساسة (خيار) |
| مركزياً | تشفير القرص + تشفير الحقول الحساسة |
| النسخ الاحتياطي | ملفات مشفّرة |
| الأسرار/المفاتيح | مخزن أسرار آمن، لا في الكود |

## 8. سجل التدقيق (Audit Log)
- يُسجِّل: من، ماذا، متى، قبل/بعد، من أي جهاز.
- **غير قابل للتعديل/الحذف** من المستخدمين العاديين.
- يشمل: الدخول/الفشل، الإدخال، الاعتماد، التعديل على المعتمد، تغييرات الصلاحيات، المزامنة، حل التعارض.
- قابل للتصفية والتصدير للمراجعة.

### 8.1 ما نُفِّذ فعلاً (v0.11)
- الكتابة موجودة منذ v0.1 عبر `write_audit` في كل عملية حسّاسة.
- **القراءة** أُضيفت في v0.11: نقاط `/api/v1/audit-log` (صفحة)، و`/facets`
  (عدّادات التصفية)، و`/export.csv` و`/export.xlsx` (تصدير)، بصلاحية `audit.view`.
- **العزل على مستوى الصفوف (RLS):** سياسة قراءة `app_can_see_hospital(hospital_id)`؛
  ولا توجد سياسة `UPDATE` ولا `DELETE` على الجدول، فالسجل غير قابل للتغيير بحكم
  التصميم. راجع الوثيقة 25 للتفاصيل والاختبارات.
- **درس مُوثَّق:** كانت الكتابة تفشل تحت RLS لأن العمود `at` له قيمة افتراضية على
  الخادم فيدفع PostgreSQL إلى `RETURNING` عند الإدراج، وهي عملية يرفضها العزل.
  الحل: تعيين `at` صراحةً في `write_audit`.

## 9. حماية البيانات الحساسة
- **لا بيانات مرضى فردية** إطلاقاً (تصميم مُجمّع).
- الإبلاغ عن الحوادث يمكن أن يكون **سرّياً** (دون هوية المُبلِّغ).
- تقليل البيانات إلى الحد الضروري (Data minimization).

## 10. النسخ الاحتياطي والاستعادة (أمنياً)
- نسخ مشفّرة، مع اختبار استعادة دوري.
- نسخة بعيدة للحماية من الكوارث.
- صلاحية الاستعادة مقيّدة (مدير النظام/المستشفى).

## 11. إدارة الثغرات والتحديثات
- تحديث التبعيات دورياً، ومراجعة الثغرات المعروفة.
- **تحديثات تطبيق Windows موقّعة** ومُتحقَّق منها.
- خطة استجابة للحوادث الأمنية (كشف، احتواء، معالجة، إبلاغ).

## 12. اختبار أمني (قائمة)
- [ ] محاولة الوصول لبيانات مستشفى آخر → مرفوضة ومسجّلة.
- [ ] محاولة تجاوز الصلاحيات عبر استدعاء API مباشر → مرفوضة.
- [ ] محاولة اعتماد ذاتي (من أدخل يعتمد) → مرفوضة.
- [ ] محاولة تعديل فترة معتمدة → مرفوضة/مسجّلة.
- [ ] إدخال بيانات ضارة (حقن SQL/XSS) → مُعالَج بأمان.
- [ ] هجوم تخمين كلمة المرور → قفل الحساب.
- [ ] الوصول دون مصادقة → مرفوض.
- [ ] تسريب بيانات في رسائل الخطأ → لا يوجد.
- [ ] تشفير الاتصال مفعّل → مؤكَّد.
- [ ] سجل التدقيق يسجّل كل العمليات الحساسة → مؤكَّد.

# الجزء الثاني: خطة الاختبار

## 13. مستويات الاختبار
| المستوى | ماذا يختبر | أمثلة |
|--------|-----------|-------|
| وحدة (Unit) | دوال ومنطق منفرد | حساب المؤشرات، قواعد اتجاه التحسن |
| تكامل (Integration) | ترابط الوحدات | إدخال → اعتماد → تقرير |
| طرف إلى طرف (E2E) | رحلة مستخدم كاملة | من الإدخال إلى الظهور في اللوحة الوطنية |
| المزامنة | سيناريوهات الانقطاع والتعارض | S1–S10 في الوثيقة 07 |
| الأمان | الصلاحيات والعزل | قائمة القسم 12 |
| الأداء | الاستجابة والحجم | آلاف السجلات، لوحات ثقيلة |
| التوطين | العربية وRTL | كل الشاشات والتقارير |
| القبول (UAT) | قبول المستخدم الفعلي | تجربة في المستشفى |

## 14. اختبارات حرجة إلزامية (لا يُقبل التسليم دونها)
1. **عدم فقدان البيانات:** كل سيناريوهات S1–S10 تنجح.
2. **عدم التكرار:** إعادة إرسال الدفعات لا تُنشئ نسخاً.
3. **حساب المؤشرات:** مطابقة الحسابات اليدوية في حالات مُعدّة (نِسب، معدلات، أعداد، متوسطات، مركّبة، اتجاه تنازلي كالعدوى).
4. **سير العمل:** لا اعتماد ذاتي، لا تجاوز خطوات، لا تعديل معتمد دون صلاحية.
5. **العزل:** كل دور لا يرى ما لا يحق له.
6. **التقارير:** PDF/Excel صحيحة عربياً ومطابقة للأرقام.
7. **العمل دون إنترنت:** كل الوظائف تعمل بلا اتصال.
8. **الاستعادة:** استعادة سليمة من نسخة احتياطية.

## 15. البيانات التجريبية
- **بيانات تجريبية واضحة** (مستشفى تجريبي، أقسام وهمية، مؤشرات بأرقام معروفة النتائج).
- **مفصولة تماماً** عن أي بيانات حقيقية (بيئة منفصلة، علم واضح).
- تُستخدم للاختبار والعرض والتدريب.

## 16. إدارة العيوب (Bugs)
- كل عيب يُسجَّل بحالته وخطورته.
- عيوب الفقدان/التكرار/الأمان = **أولوية قصوى**.
- لا يُعتبر الإصدار جاهزاً ومعه عيب حرج مفتوح.

## 17. معايير "تم" (Definition of Done)
- الميزة مُنفَّذة ومختبرة (وحدة + تكامل + E2E حيث ينطبق).
- اختبارات المزامنة/الأمان ذات الصلة تمر.
- الواجهة عربية RTL سليمة.
- التوثيق محدَّث.
- لا عيوب حرجة مفتوحة.

## 18. البيئات
| البيئة | الغرض |
|-------|-------|
| تطوير (Dev) | بناء واختبار سريع ببيانات تجريبية |
| اختبار (Staging) | محاكاة قريبة من الإنتاج + اختبار قبول |
| إنتاج (Prod) | التشغيل الفعلي (بيانات حقيقية) |
- فصل صارم بين بيئة الاختبار والإنتاج؛ **لا بيانات حقيقية في الاختبار**.
