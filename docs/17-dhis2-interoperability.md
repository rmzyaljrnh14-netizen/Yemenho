# التكامل مع منظومة المعلومات الصحية الوطنية (DHIS2)
## النظام الوطني لإدارة مؤشرات الأداء الصحي والجودة وسلامة المرضى — وزارة الصحة العامة والسكان

**الإصدار:** 1.1 · **الحالة:** مسودة بانتظار الموافقة

---

## الشرح بلغة بسيطة
اليمن تملك **منظومة معلومات صحية وطنية قائمة (DHIS2)** تُدار من الوزارة وتجمع بيانات الخدمات. نظامنا لا يلغيها؛ **يكمّلها** في جانب الجودة وسلامة المرضى. هذه الوثيقة تشرح كيف "يتكلّمان" النظامان معاً.

---

## 1. المبدأ: تكامل لا تنافس
- **DHIS2** = جمع بيانات الخدمات والإبلاغ الإحصائي الدوري على مستوى المنشأة.
- **نظامنا** = قياس الجودة وسلامة المرضى تفصيلاً داخل المستشفى/القسم + المزامنة + العمل دون إنترنت.
- **العلاقة:** نظامنا مصدر إثراء؛ يُرسل خلاصة مؤشرات الجودة إلى DHIS2 حيث تتقاطع التعريفات.

## 2. أين يتقاطع النظامان؟
| المجال | في DHIS2 | في نظامنا |
|-------|---------|-----------|
| مؤشرات الخدمات (تغطية، أعداد) | ✅ المرجع | يستقبل/يواءم عند الحاجة |
| مؤشرات الجودة وسلامة المرضى | محدود | ✅ التخصّص |
| العمل دون إنترنت داخل القسم | محدود | ✅ أساسي |
| الحوادث/RCA/CAPA | غير مغطّى | ✅ كامل |
| التقارير الوطنية المجمّعة | ✅ قوي | ✅ (لوحات جودة) |

## 3. نموذج التكامل (Interoperability)

### 3.1 الطبقة الأولى — المواءمة (Alignment)
- توحيد **التعريفات** و**وحدات القياس** و**الدوريات** حيث تتقاطع المؤشرات.
- استخدام نفس **الرموز** أو ربط الرموز بين النظامين (Mapping Table).

### 3.2 الطبقة الثانية — التصدير (Export)
- نظامنا يُنتج **ملف تصدير** بمؤشرات الجودة بصيغة يقرأها DHIS2.
- **الخيارات:**
  - **ملف بيانات (CSV/JSON) بهيكل محدّد** يُستورد يدوياً/نصف آلياً.
  - **تكامل API** إن سمحت بنية DHIS2 بالوصول (نقطة `dataValueSets`).
- **التردد:** شهري/ربعي حسب اتفاق الوزارة.

### 3.3 الطبقة الثالثة — الربط الحي (Live, لاحقاً)
- عند توفر الشروط التقنية والموافقات: ربط مباشر عبر API.
- **آمن:** بلا بيانات مرضى، وبصلاحية مقيّدة، وبسجل تدقيق.

## 4. جدول الربط (Mapping)
```sql
CREATE TABLE dhis2_mappings (
  id                TEXT PRIMARY KEY,
  local_indicator_id TEXT,
  dhis2_data_element TEXT,     -- معرّف العنصر في DHIS2
  dhis2_category     TEXT,
  conversion_factor  REAL DEFAULT 1,
  notes              TEXT,
  created_at TIMESTAMP
);
```

## 6. اعتبارات التكامل
- **لا تكرار إدخال:** حيث تتقاطع البيانات، نهدف لإدخال واحد ومصدر واحد للحقيقة.
- **الأمانة:** التصدير يحمل المصدر وتاريخه وعدم اليقين.
- **التوافق:** أي تغيير في هيكل التصدير = إصدار جديد بمخطط موثّق.
- **الصلاحية:** من يُصدّر يملك صلاحية، وكل تصدير مسجّل.

## 7. المراحل
| المرحلة | المخرج |
|--------|--------|
| 1. دراسة DHIS2 | فهم العناصر والفئات ونقاط API المتاحة |
| 2. جدول الربط | مطابقة مؤشراتنا بعناصر DHIS2 |
| 3. تصدير ملف | ملف قابل للاستيراد |
| 4. اختبار التطابق | التأكد أن القيم تصل صحيحة |
| 5. ربط حي (اختياري) | تكامل API عند الموافقة |

## 8. المخاطر والقيود
- **قيود تقنية:** قد لا تتوفر نقاط API للكتابة في DHIS2 → نكتفي بالملفات.
- **قيود حوكمية:** الربط يحتاج موافقة الوزارة والإدارة المسؤولة عن DHIS2.
- **اختلاف التعريفات:** بعض المؤشرات قد لا تتقاطع → تبقى في نظامنا فقط.
- **البنية التحتية:** ضعف الاتصال يؤثر على الربط الحي.

## 9. مبدأ أمانة
- **لا نزعم تكاملاً قائماً** قبل تنفيذه واختباره فعلياً.
- المرحلة الأولى: **تصدير ملف** (ممكن دائماً). الربط الحي **هدف لاحق** بشروط.
